1What SENA is, in 60 seconds

SENA is an Australian NDIS (disability services) onboarding platform. The piece this doc concerns is a voice agent that walks a participant through 6 onboarding screens by speaking with them. The conversation is full duplex audio over the network.

ComponentStackWhere
Mobile app (participant)Flutter + GetXrepo root lib/
Voice backendPython 3.12 + FastAPI + WebSocketsSENA_AI/sena-ai/services/onboarding/
Speech-to-speech modelGoogle Gemini Live API (model gemini-3.1-flash-live-preview)cloud
State storeRedislocal dev container, prod EC2

Audio path:

Flutter mic   ─[ws]─►  FastAPI server  ─[ws]─►  Gemini Live
                              │                       │
Flutter speaker ◄─[ws]──   server forwards ◄─[ws]─  Gemini audio reply

Gemini decides on its own when the user is done talking (voice activity detection — VAD), then it speaks back. Our server is a thin bridge — it does NOT do VAD.

2The bug — exact signature

Mid-session the agent stops responding entirely. WebSocket stays open. No exception. No close frame from Gemini. The participant talks, server forwards every byte, Gemini eats them, but never produces a reply. The session looks alive but is functionally dead until the user gives up and ends it manually.

Reproduction

  • Open onboarding session, get past the agent's opening greeting (turn 1 completes cleanly with audio output).
  • Participant starts talking to answer.
  • Sometimes turn 2 fires normally; other times the session never produces turn 2. Non-deterministic.
  • Repros on Steps 1–6 (not screen-specific).
  • Single tenant, local dev — but the cause is network-side, not local-only.

Log signature (real capture, this is what diagnoses it)

Read the gap: 14 seconds between turn_complete and client_stop. During that window — mic open, audio flowing, server forwarding — there is zero user_said (input transcription), zero turn_start, zero agent_said, zero error, zero go_away. Just dead air from Gemini's side.

3Root cause (it is NOT an internal error)

Common wrong guess: "There must be an internal error happening in the background that isn't logged." It is not. There IS no error. Stop hunting for one.

What's actually happening:

  1. Gemini Live uses voice activity detection (VAD) to decide when the user finished speaking. The backend does not control this — Gemini does it server-side on Google's infrastructure.
  2. Our current VAD config is END_SENSITIVITY_LOW + silence_duration_ms=3000 — i.e. Gemini needs 3 full seconds of clearly-silent audio before it considers the user done.
  3. If any ambient noise leaks into those 3 seconds — breathing, keyboard, fan, the user's own speakers playing back the agent's previous reply — Gemini keeps the activity flag latched ON. Forever.
  4. With activity latched, Gemini never starts a new turn. The receive iterator on our side (async for msg in session.receive()) blocks indefinitely, waiting for a message that will never arrive.
  5. The TCP socket stays alive. The Python task is healthy. Nothing logs. Hence "silent freeze."

The model is gemini-3.1-flash-live-preview. It is a preview model with a documented VAD edge-case family (Google's generative-ai repo, cookbook issue #1197 and adjacent) where post-kickoff VAD doesn't re-arm cleanly. Our config tolerance to ambient noise compounds it.

Two failure modes the fix has to cover

ModeTriggerWhat stops it
A — Ambient wedgeBackground noise (or echo of agent's reply through speakers) into a mic that stays open while the user thinksTighter VAD end-sensitivity AND mic muted while agent is speaking
B — Preview-model wedgeInternal Gemini bug after turn 1; mic input lands but VAD doesn't re-armClient-side explicit audio_stream_end on user pause + watchdog that detects the stall and reconnects

The changes below cover BOTH modes — we don't try to discriminate first because both fixes are safe and additive.

4Backend Change 1 — VAD end-sensitivity BACKEND

File: sena-ai/services/onboarding/src/onboarding/services/gemini_live.py
Line: ~246–264, inside run() where LiveConnectConfig is built.

Find

realtime_input_config=types.RealtimeInputConfig(
    automatic_activity_detection=types.AutomaticActivityDetection(
        disabled=False,
        start_of_speech_sensitivity=types.StartSensitivity.START_SENSITIVITY_LOW,
        end_of_speech_sensitivity=types.EndSensitivity.END_SENSITIVITY_LOW,
        prefix_padding_ms=20,
        silence_duration_ms=3000,
    ),
    activity_handling=types.ActivityHandling.START_OF_ACTIVITY_INTERRUPTS,
    turn_coverage=types.TurnCoverage.TURN_INCLUDES_ONLY_ACTIVITY,
),

Replace with

realtime_input_config=types.RealtimeInputConfig(
    automatic_activity_detection=types.AutomaticActivityDetection(
        disabled=False,
        # START_SENSITIVITY_LOW — do NOT change to HIGH. HIGH fires VAD on
        # ambient noise between turns and the model starts "responding" to
        # silence.
        start_of_speech_sensitivity=types.StartSensitivity.START_SENSITIVITY_LOW,
        # END_SENSITIVITY_HIGH — Gemini closes the user's turn faster when
        # the audio level drops, even if some residual ambient hum is still
        # in the stream. This is the freeze fix for failure mode A. With LOW
        # the model could wait indefinitely; HIGH closes after a clean drop.
        end_of_speech_sensitivity=types.EndSensitivity.END_SENSITIVITY_HIGH,
        prefix_padding_ms=20,
        # 1500 ms — shorter silence-to-close. With HIGH end-sensitivity 3000
        # is overkill and lets ambient creep back in. 1500 keeps natural-
        # sounding turn handoff without giving ambient time to wedge.
        silence_duration_ms=1500,
    ),
    activity_handling=types.ActivityHandling.START_OF_ACTIVITY_INTERRUPTS,
    turn_coverage=types.TurnCoverage.TURN_INCLUDES_ONLY_ACTIVITY,
),

If this makes VAD fire too aggressively (agent starts replying before the participant finishes a thought), bump silence_duration_ms back up in 500 ms steps — 1500 → 2000 → 2500. Do NOT revert end_of_speech_sensitivity to LOW; that's what's causing the wedge.

5Backend Change 2 — heartbeat probe BACKEND

File: same — sena-ai/services/onboarding/src/onboarding/services/gemini_live.py
Location: inside _gemini_to_browser(session), immediately before the outer while True: loop that wraps async for msg in session.receive().

Why: proves which loop is blocked the next time it freezes. If heartbeat keeps printing while no turn_start fires, the receive iterator is stuck inside the SDK (VAD wedge). If heartbeat stops printing, the task died silently (different bug entirely).

Add this block

import time as _time  # if not already imported (file already imports time at top)

# ── Heartbeat probe ───────────────────────────────────────────────────────
# Logs once every 5s with the time since the LAST Gemini message was received.
# When the freeze recurs:
#   - Heartbeat keeps firing, since_last_msg keeps growing → VAD wedge
#     confirmed (SDK iterator is blocked, not the asyncio task).
#   - Heartbeat stops firing → the receive task itself died silently. Different
#     bug — escalate.
self._last_gemini_msg_at = _time.monotonic()   # add as instance field in __init__

async def _heartbeat() -> None:
    while True:
        await asyncio.sleep(5.0)
        gap = _time.monotonic() - self._last_gemini_msg_at
        log.info(
            "g2b_heartbeat session=%s since_last_msg_s=%.1f",
            self._session_id,
            gap,
        )

_hb_task = asyncio.create_task(_heartbeat())
try:
    # … existing while-True / async-for body unchanged …
    pass
finally:
    _hb_task.cancel()

Where the existing receive loop does async for msg in session.receive(), update the anchor on every iteration:

async for msg in session.receive():
    self._last_gemini_msg_at = _time.monotonic()   # heartbeat anchor
    # … existing handling …

6Backend Change 3 — VAD-silence watchdog WARN BACKEND

File: same.
Location: existing _silence_monitor coroutine (already in the file — search for self._silence_warned).

Why: single grep-able log signature for every future occurrence. Turns "we never know what the exact error was" into "we know exactly when VAD wedged."

Step 1 — add supporting fields in __init__

self._audio_chunks_since_turn_complete: int = 0
self._last_turn_complete_at: float = 0.0

Step 2 — maintain them in the right places

  • Inside the existing turn_complete handler (where turn_complete WS event is emitted to the client), set self._last_turn_complete_at = _time.monotonic() and reset self._audio_chunks_since_turn_complete = 0.
  • Inside _browser_to_gemini where audio chunks are received from the client and forwarded to Gemini, increment self._audio_chunks_since_turn_complete += 1 after the forward call.

Step 3 — add the WARN branch inside _silence_monitor

# Inside _silence_monitor, in the periodic check loop, AFTER the existing
# silence-prompt branch:

since_turn_complete = _time.monotonic() - self._last_turn_complete_at
if (
    self._last_turn_complete_at > 0.0
    and since_turn_complete > 6.0
    and self._audio_chunks_since_turn_complete > 50    # mic clearly open
    and not self._gemini_is_speaking
    and self._turn_id > 0                              # past kickoff
):
    log.warning(
        "gemini_vad_silent_after_turn_complete "
        "session=%s since_turn_complete_s=%.1f audio_chunks_sent=%d turn=%d",
        self._session_id,
        since_turn_complete,
        self._audio_chunks_since_turn_complete,
        self._turn_id,
    )
    # Mitigation — force-flush Gemini's input buffer. Sometimes this is enough
    # to break a wedge in the preview model (failure mode B). Cheap to try.
    try:
        await session.send_realtime_input(audio_stream_end=True)
    except Exception:
        pass  # if the session itself is broken, this throws; we already warned.
    # Reset the chunk counter so we don't WARN-spam every 5s.
    self._audio_chunks_since_turn_complete = 0

7Flutter Change 1 — mic-mute during agent speech FLUTTER

Why: when the agent is speaking, the phone's speaker plays Gemini's reply. If the mic is open at the same time, the speaker audio loops back into the mic, travels through our WebSocket, reaches Gemini, and Gemini's VAD registers it as "user still talking." VAD never closes → freeze. Failure mode A.

This is a preventive change — without it, change 1 (VAD end-sensitivity) won't fully fix the freeze on devices without strong echo cancellation.

Where to put the gate (Flutter)

In the voice-onboarding feature, in the controller that owns the mic stream listener. Typically:

lib/features/voice_onboarding/presentation/controllers/voice_session_controller.dart

Search for the WebSocket event handler — the switch/case (or VoiceEventModel.parse) that dispatches on the type field of the incoming WS frame.

Required behaviour

  1. Maintain a controller field final RxBool agentSpeaking = false.obs; (or a plain bool _agentSpeaking = false; if you don't want it reactive).
  2. On WebSocket event turn_start (server → client): agentSpeaking.value = true;
  3. On WebSocket event turn_complete: agentSpeaking.value = false;
  4. On WebSocket event interrupted: agentSpeaking.value = false;
  5. In the mic stream listener (the callback that receives raw PCM chunks from the recorder), gate the send, not the recorder:
// In the mic chunk listener:
_micStream.listen((Uint8List chunk) {
  if (agentSpeaking.value) return;     // drop, don't send while agent talks
  _ws.add(jsonEncode({
    'type': 'audio_chunk',
    'data': base64Encode(chunk),
  }));
});

Do NOT stop and restart the recorder on every turn. That introduces start-up latency and clips the first 100–200 ms of the participant's reply. Gate the SEND, not the CAPTURE.

Optional polish

Drive a visual mic-state indicator off agentSpeaking (icon dims while agent talks, lights when user can speak). UX win, no extra wiring.

8Flutter Change 2 — stall detection + auto-resume FLUTTER

Why: change 3 (server WARN) catches the wedge on the server, but the participant is still stuck. The mobile app should detect the same stall and either retry or surface a clean message — never sit at a dead mic icon.

Stall detector (Flutter side)

Track three timestamps on the voice controller:

DateTime? _lastTurnCompleteAt;     // set on every turn_complete event
DateTime? _lastUserSaidAt;         // set on every user_said event
DateTime? _lastAgentReplyStart;    // set on every turn_start event

Run a Timer.periodic(Duration(seconds: 3)) while the session is active. On each tick:

void _checkStall(Timer _) {
  if (_lastTurnCompleteAt == null || agentSpeaking.value) return;
  final since = DateTime.now().difference(_lastTurnCompleteAt!);
  // 8 seconds is well beyond the longest natural user pause
  // (1.5s silence threshold post-fix + 2s utterance + safety margin).
  if (since.inSeconds >= 8 && _lastUserSaidAt == null) {
    _onStallDetected();
  }
}

What _onStallDetected should do

  1. First attempt — send a JSON control frame {"type": "client_force_turn_end"} over the WS. (Server-side already calls send_realtime_input(audio_stream_end=True) from backend change 3 when its own watchdog fires; both paths converge on the same mitigation.)
  2. Wait 4 more seconds. If turn_start fires, recovered — log it and continue.
  3. If still nothing — close the WS, request a fresh session via the existing resumable handle the server sends on go_away events (Flutter should already be storing this; if not, add it).
  4. Show a brief one-line snackbar: "Reconnecting…". Never crash, never go silent.

The resumable handle endpoint already exists server-side at POST /v1/onboarding/session/{id}/resume. It returns a new session id that picks up the conversation history. Flutter just needs to call it and open a fresh WS.

Server-side handler for the new client frame

Bonus backend tweak (small, paired with Flutter change 2): in _browser_to_gemini, add a case for the new client_force_turn_end message:

elif msg_type == "client_force_turn_end":
    # Flutter-side stall detector hit its threshold and asked us to flush.
    # Mirror what the server's own watchdog does (backend change 3).
    await session.send_realtime_input(audio_stream_end=True)
    log.info(
        "client_forced_turn_end session=%s",
        self._session_id,
    )

9Verification steps

  1. Backend tests: cd sena-ai/services/onboarding && python -m pytest tests/ -x -q — should be green after backend changes.
  2. Start onboarding service locally: uvicorn src.onboarding.main:create_app --factory --reload --port 8083.
  3. Open Flutter app, point at http://<dev-host>:8083, start a voice onboarding session.
  4. Complete the agent's opening greeting, then answer naturally. Verify turn 2 fires every time across 10 consecutive turns.
  5. In server logs, confirm no gemini_vad_silent_after_turn_complete WARN appears during a normal session, and a g2b_heartbeat line appears every ~5s.
  6. Force a freeze for negative test: temporarily revert backend change 1 only (VAD back to END_SENSITIVITY_LOW, silence_duration_ms=3000), keep the watchdog and heartbeat. Reproduce the freeze. Confirm the WARN now fires with all expected fields populated. Re-apply backend change 1.
  7. Flutter side: with airpods/headphones off (phone speaker only), still no freeze. Then with agentSpeaking mic-mute disabled in code (just for the test), reproduce the freeze — confirms the mute change is doing real work.

10Acceptance criteria

  • 10 consecutive turns, phone speaker only, no headphones — zero freezes.
  • Server logs show g2b_heartbeat roughly every 5 s during a session.
  • Server logs show no gemini_vad_silent_after_turn_complete WARN during a normal flow.
  • Flutter UI never sits at a dead mic for >8 s without either recovering or showing the "Reconnecting…" message.
  • flutter analyze = 0 warnings.
  • ruff check sena-ai/services/onboarding/src/ = clean.
  • mypy sena-ai/services/onboarding/src/onboarding/ = clean.

12Things to NOT do (saves a debugging cycle)

  1. Do NOT add a server-side _agent_speaking flag that gates the mic forward in _browser_to_gemini. This was the original SENA failure mode (documented in .claude/issues-solved/0001-vad-dies-after-few-turns.md): the gate causes VAD to die after 2–4 turns silently. Mic gating belongs on the client (Flutter), not the server. The server forwards every byte unconditionally — let Gemini's VAD decide.
  2. Do NOT change the model id from gemini-3.1-flash-live-preview to a 2.x model. The 2.x family (gemini-2.5-flash-native-audio-*, gemini-live-2.5-flash-preview, gemini-2.0-flash-live-001) is deprecated/shut down. 3.1 is the current.
  3. Do NOT use session.send(input=..., end_of_turn=True) anywhere. Old API. Use session.send_realtime_input(audio=..., text=..., audio_stream_end=...) with the specific kwarg.
  4. Do NOT use send_client_content(...) for new user messages. That method is for seeding initial history only. New messages mid-conversation go through send_realtime_input.
  5. Do NOT add a "periodic flush loop" that fires a forced turn cycle every N seconds. Tempting but harmful — it cuts the model off mid-thought, introduces new bugs, and the documented Gemini docs do not list a "transcription engine degradation" failure mode that would justify it. The watchdog (backend change 3) does targeted flushing only WHEN a stall is detected, which is the correct pattern.
  6. Do NOT raise start_of_speech_sensitivity to HIGH. HIGH fires VAD on ambient noise between turns and the model "responds" to silence. Keep START_SENSITIVITY_LOW. Only change end_of_speech_sensitivity.
  7. Do NOT delete the kickoff shield (_kickoff_shield_active field, ~line 122–134 of gemini_live.py). It protects turn 0 against a different VAD wedge variant; removing it re-introduces a separate freeze on session start.
  8. Do NOT stop and restart the Flutter recorder on turn boundaries. Causes 100–200 ms of audio clipping at the start of every user reply, makes the assistant miss the first word. Gate the SEND inside the mic stream listener, not the recorder lifecycle.
