SENA Onboarding — Voice Context Refresh: Option Comparison

Goal: keep Gemini Live's view of FormState coherent across mid-session field changes without poisoning VAD or creating dual writers. Model in use: gemini-3.1-flash-live-preview.

1. The problem (today, in production)

+---------------------------------------+ | Gemini Live working memory | +---------------------------------------+ | | | WRITER #1 (frozen at connect time) | stale after first edit | +---------------------------------+ | | | system_instruction: | | | | __TURN_JSON__ = { | | | | visible_fields: [...], | | | | next_target: ..., | | | | last_rejection: ... | | | | } | | | +---------------------------------+ | | + | | WRITER #2 (live, per-turn) | conversational drift | +---------------------------------+ | | | user: "change my DOB to 5/5/01" | | | | assistant: "got it" | | | | user: "my name is Jane now" | | | +---------------------------------+ | | | | | v | | context-window | | compression | | | | | v | | HALLUCINATED VALUES | | (compressor smashes the two | | copies into one ambiguous | | summary) | | | +---------------------------------------+

Three reported issues all trace to two writers, one field:

  1. #1 Stale screen JSON during live connection
  2. #2 Memory state conflict / duplication
  3. #3 Hallucination from compression of conflicting state

4. Option D explained visually (the one you didn't grok)

The idea in one sentence

Every time the model calls a tool, the tool's return value ships back a fresh full snapshot of FormState. The model then reads from "what the tool just told me" instead of "what was in the system prompt at session start." No new SDK surface. No reconnect. No VAD interaction.

Today's flow (BROKEN)

session start │ │ system_instruction = "...prompt... __TURN_JSON__={visible_fields:[{path:'basics.name', value:null}]}..." ▼ [Gemini Live frozen view: name=null] │ │ user: "my name is Jane" ▼ model calls update_field(section="basics", field="name", value="Jane") │ │ tool returns: {"ok": true} ← only "ok", no fresh state ▼ [Gemini Live working memory NOW:] ├─ frozen system_instruction says name=null ← STALE ├─ conversation says "Jane" (from user) ← drift └─ tool result says "ok" ← no state │ ▼ user: "what's my name on file?" │ ▼ model has 2 conflicting answers in memory → hallucinates "Janet"

Option D flow (FIXED)

session start │ │ system_instruction = "...prompt..." ← NO bootstrap JSON, or minimal ▼ [Gemini Live view: no state — model knows to wait] │ │ first turn: model calls get_current_state() → returns full FormState ▼ [Gemini Live view: name=null (from tool, not from prompt)] │ │ user: "my name is Jane" ▼ model calls update_field(section="basics", field="name", value="Jane") │ │ tool returns: { │ "ok": true, │ "saved": {"section":"basics", "field":"name", "value":"Jane"}, │ "state": { ← NEW: fresh full snapshot │ "visible_fields": [{path:"basics.name", value:"Jane"}, │ {path:"basics.dob", value:null}, ...], │ "next_target": {path:"basics.dob", ...}, │ "prior_steps": {...} │ } │ } ▼ [Gemini Live working memory:] ├─ system_instruction has no state to be stale about ← ONE writer only └─ latest tool result has full fresh state ← AUTHORITATIVE │ ▼ user: "what's my name on file?" │ ▼ model reads from latest function_response.state → answers "Jane" correctly

The prompt rule that makes this work

## 1. Source of truth

Your source of truth is the state field in the most recent
function_response in this conversation. The bootstrap state block (§8) is
your starting state for the very first turn ONLY. Every subsequent
update_field, add_row, etc. returns a fresh state snapshot —
that is the new truth. Never combine information from §8 with the
latest function_response.

6. Recommendation

Ship Option D this week. It uses a doc-blessed Gemini channel, works on 3.1, eliminates all 3 reported issues, ~1-day diff, and doesn't conflict with PLAN #1 (per-screen reconnect) which can ship later as the prompt-adherence polish step.

Why not B alone: it's the right long-term shape but costs 15 subtasks and won't solve mid-screen field edits even after shipping. D handles those too.

Why not A alone: yes it removes the conflicting writer, but the model loses its bootstrap snapshot — first-turn it has no context at all. D keeps a tiny header + lets tool returns hydrate the rest.
