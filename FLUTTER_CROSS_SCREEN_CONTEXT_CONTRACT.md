# Cross-Screen Context — Flutter Integration Contract

**Audience:** Flutter developer wiring the SENA voice onboarding into the multi-step participant flow.
**Backend status:** Server-side cross-screen context is built, tested, and live (89/89 tests, default flag `ON`). Everything in this document is the wire contract Flutter must satisfy for it to actually work end-to-end.
**Updated:** 2026-05-08

---

## TL;DR (read this first)

The voice agent has **no in-memory continuity** between voice sessions. Every time the user opens the voice sheet, a brand-new Gemini Live session starts and the model has zero conversation history. To make the agent appear continuous across screens (step 1 → step 2 → step 3 → next-day return), the **server reconstructs prior context from Redis on every session create** using two stable identifiers Flutter must supply:

- `tenant_id` — the organization the participant belongs to
- `participant_id` — the participant themselves

Redis holds, for each `(tenant_id, participant_id)` pair, a 7-day-TTL bucket of "step summaries" — one per completed onboarding step. On the next session create the server reads that bucket and injects the relevant facts into the new agent's system prompt. The agent then says "Hi Jane, I see you already gave us your contact details on step 1 — let's pick up with NDIS plan."

**What Flutter must do:**

1. Send `tenant_id` and `participant_id` on **every** `POST /v1/onboarding/session` call. Empty values silently disable the feature.
2. Use **the same** `participant_id` across every step for the same human user. Never regenerate it per step.
3. When the user navigates between steps mid-session, **close the current voice WS and open a new one** with the same identifiers — do not reuse the WS across steps.
4. Optionally pass a `bootstrap.prior_pages` map for in-app same-session handoff (data Flutter already has locally). The server merges this with the Redis bucket — Flutter's `prior_pages` always wins.

**That's it.** No Flutter side has to read or write Redis. The server owns the bucket; Flutter just supplies the keys.

## Why this exists (the problem)

### Without cross-screen context

```
[Step 1 voice session]
  Agent:  "Hi! What's your name?"
  User:   "Jane Smith."
  ...
  User taps Next →
[Step 2 voice session — brand-new Gemini connection, zero memory]
  Agent:  "Hi! What's your name?"          ← BUG. User just told it.
```

### With cross-screen context

```
[Step 1 voice session]
  Agent:  "Hi! What's your name?"
  User:   "Jane Smith."
  ...
  Step 1 completes → server writes step summary to Redis bucket.

  User taps Next →

[Step 2 voice session — new Gemini connection, but server hydrates context]
  POST /v1/onboarding/session with tenant_id + participant_id
  Server reads bucket: {step:1: {full_name: "Jane Smith", phone: "+61...", ...}}
  Server injects into [LIVE_STATE_JSON].prior_pages
  Agent's system prompt is now aware of step 1 facts.

  Agent:  "Hi Jane! Welcome to the NDIS plan step. We've got your contact
           details from earlier — now I'd like to ask about your plan."
```

The agent is stateless; Redis + the system prompt is the entire memory.

## Identity contract — `tenant_id` and `participant_id`

These two values are the bucket key. Get them wrong and the bucket misses (silent feature-off). Get them right and everything Just Works.

### Where they come from

| Identifier | Source in Flutter | Lifetime | Format |
|---|---|---|---|
| `tenant_id` | Logged-in organisation context (`Get.find<OrgContext>().currentOrgId` or wherever the app stores active org) | Stable for the user's full membership in that org | Server-issued UUID (string) |
| `participant_id` | Logged-in participant profile (`Get.find<AuthController>().currentUser.participantId`) | Stable for the participant's lifetime in this tenant | Server-issued UUID (string) |

These are **NOT generated by Flutter on the fly**. They come from your existing auth + org context. If the user switches organisations (multi-tenant flows), the participant_id changes — that's correct, because cross-org context must not leak.

### Hard rules

1. **Same `participant_id` across every step** for the same human user. If step 1's `participant_id` is `p-abc123`, step 2's session create MUST also use `p-abc123`. Don't generate a new UUID per step.
2. **Both must be non-empty** for the feature to engage. Empty string or null → server skips the bucket lookup, logs a warning (`session_create_tenant_id_missing`), and the agent boots with no prior context. No crash, just silent feature-off.
3. **Never let the user input these directly.** They come from auth; they are not form fields. A test harness may type them in, but production reads them from the auth context.
4. **Never reuse `participant_id` across tenants.** The server prefixes Redis keys by `tenant_id` so cross-tenant leakage is impossible by construction, but you should not be sending one tenant's participant ID under another tenant's `tenant_id` regardless.

### What happens if you get it wrong

| Mistake | Symptom | Server log line |
|---|---|---|
| `tenant_id` empty | Agent has no prior context on step 2+ | `session_create_tenant_id_missing` |
| `participant_id` differs between steps | Step 2 agent acts like a fresh user | `session_create_resolved_bootstrap` shows `prior_pages_keys=[]` |
| `participant_id` reused across tenants | Wrong participant's data leaks (server-side this can't happen; the bucket key includes both) | n/a — physically impossible |

## Wire contract

### `POST /v1/onboarding/session`

#### Request body (the one Flutter must construct)

```json
{
  "participant_id": "p-abc123",
  "tenant_id":      "t-xyz789",
  "schema":         { /* full StepSchema for the current step */ },
  "bootstrap": {
    "mode": "page_handoff",
    "participant_display_name": "Jane",
    "current_page_values": { },
    "readonly_paths": [ ],
    "prior_pages": { }
  }
}
```

| Field | Required | Purpose |
|---|---|---|
| `participant_id` | YES | Bucket key. Stable across all steps for the same user. |
| `tenant_id` | YES | Bucket key. From the logged-in org context. Empty → cross-screen feature silently OFF. |
| `schema` | YES | Full StepSchema for the step the user is now on. (Same schema you've been sending.) |
| `bootstrap.mode` | recommended | `new_user` / `returning_same_page` / `page_handoff`. See selection rule below. |
| `bootstrap.participant_display_name` | recommended | Drives the agent's name use in greetings (Rule 2 / "ADDRESS THE PARTICIPANT"). |
| `bootstrap.current_page_values` | optional | Flat map `{section.field: value}` of values already saved on THIS step (e.g. user typed something earlier and refreshed). |
| `bootstrap.readonly_paths` | optional | Paths the agent must not try to update (e.g. `["basics.email"]`). |
| `bootstrap.prior_pages` | optional | `{step_id: {section.field: value}}` from earlier completed steps. **If empty AND `tenant_id` is set AND the feature flag is on, the server auto-fills this from the Redis bucket.** Flutter's value always wins if non-empty. |

#### `bootstrap.mode` selection rule

```dart
String pickMode({
  required bool hasLocallyKnownPriorSteps,
  required bool currentPageHasPrefills,
  required bool participantHasAnyHistory,
}) {
  if (hasLocallyKnownPriorSteps) return 'page_handoff';
  if (participantHasAnyHistory)  return 'page_handoff';   // let server hydrate from bucket
  if (currentPageHasPrefills)    return 'returning_same_page';
  return 'new_user';
}
```

When in doubt, send `page_handoff`. The server's bucket lookup is harmless and additive — if the bucket is empty, the agent falls back to a generic greeting on its own.

### Headers (auth + session ownership)

The WS upgrade and the state read/write endpoints use these for ownership assertion:

```
X-Tenant-Id:      <same tenant_id>
X-Participant-Id: <same participant_id>
Authorization:    Bearer <jwt>  // standard auth
```

Send all three on:
- `WSS /ws/onboarding/{session_id}`
- `GET/PUT /v1/onboarding/session/{session_id}/state`
- `POST /v1/onboarding/session/{session_id}/complete`

If the headers' `(tenant, participant)` doesn't match the session's, the server returns 403 (cross-tenant guard).

## Server behaviour you can rely on

This is what the server does so you know what to expect — you don't implement any of it.

### Bucket read — triggered by

`POST /v1/onboarding/session` → if all of:
- `settings.onboarding_cross_screen_context_enabled == True` (default ON)
- `req.tenant_id` non-empty
- `bootstrap.prior_pages` is empty (Flutter didn't supply its own)

…then server calls `UserContextRepo.get_bucket(tenant_id, participant_id)`, hydrates `bootstrap.prior_pages` from the result, and proceeds. Logs `session_create_resolved_bootstrap` with `prior_pages_keys` for diagnostics.

### Bucket write — triggered by

Two paths converge on `UserContextRepo.put_step_summary`:

1. **Step completion** (`POST /v1/onboarding/session/{id}/complete`, OR `advance_step` tool from voice).
2. **WS close best-effort flush** — if the user disconnects mid-step but enough is filled, server writes a partial summary on close.

Both are idempotent on `(participant_id, step_number)` — re-running them overwrites the same Hash field.

### Bucket key shape (FYI — Flutter doesn't construct these)

```
Hash:  sena:onboarding:user_ctx:{tenant_id}:{participant_id}
       field "step:1" → JSON StepSummary
       field "step:2" → JSON StepSummary
       ...

Set:   sena:onboarding:user_idx:{tenant_id}:{participant_id}
       members = {session_id_1, session_id_2, ...}
```

Both keys carry **7-day TTL refreshed on every write**. A user who returns within 7 days gets full continuity; after 7 days the bucket ages out and the agent will need to re-collect.

### Cross-screen context feature flag

```
SENA_AI_ONBOARDING_CROSS_SCREEN_CONTEXT_ENABLED   # default: true
```

If turned off, the server skips both reads and writes and the agent has no cross-step memory. Flutter behaviour does not need to change either way — sending `tenant_id`/`participant_id` is harmless when the flag is off.

## Step navigation — the part that's currently missing in Flutter

This is the gap that causes "user navigated to step 2 but agent still asks step-1 questions".

### Rule

**One voice WS = one step.** Period. When the user navigates between steps, Flutter MUST close the current voice WS and open a new one for the new step.

### Required Flutter implementation

```dart
// Inside the controller that drives the multi-step screen header (Next / Back)
Future<void> goToStep(StepId newStep) async {
  if (voiceCtrl.isConnected.value) {
    // Build prior_pages from steps THIS APP knows are completed.
    // The server will merge / overwrite from the bucket as needed.
    final priorPages = <String, Map<String, dynamic>>{};
    for (final s in onboardingCtrl.completedSteps) {
      priorPages[s.id] = s.publicValuesForVoiceContext();   // flat {section.field: value}
    }

    // Close current WS gracefully — code 4001 = "step_change", server skips resume.
    await voiceCtrl.disconnect(reason: 'step_change');

    // Hand control back to the navigator so the new step screen mounts.
    // (UI does its normal navigation transition here.)
    await router.goToStep(newStep);

    // Open a fresh voice session for the new step. Same tenant/participant.
    await voiceCtrl.connect(
      tenantId:      auth.tenantId,
      participantId: auth.participantId,
      stepId:        newStep,
      schema:        schemaFor(newStep),
      bootstrap: BootstrapEnvelope(
        mode: priorPages.isEmpty ? 'new_user' : 'page_handoff',
        participantDisplayName: profile.displayName,
        priorPages: priorPages,
        currentPageValues: stepCtrl.currentValues,    // anything already saved on the new step
        readonlyPaths:     stepCtrl.readonlyPaths,
      ),
    );
  } else {
    // Voice sheet wasn't open — just navigate.
    await router.goToStep(newStep);
  }
}
```

### What `publicValuesForVoiceContext` should return

A flat map of facts safe for the agent to "remember" — typically the user-provided values for that step, with sensitive PII redacted if your policy requires it:

```dart
// For step 1 (personal information):
{
  'basics.full_name': 'Jane Smith',
  'basics.phone':     '+61400000000',
  'basics.preferred_language': 'English',
  // …skip read-only / system fields like email if your tenant policy blocks them
}
```

The server stores this verbatim. The agent will read it back to the user only if asked ("what name do you have for me?" → answers from the map per Rule 11).

## Verification scenarios

Run these in order. If any fails, the cross-screen context contract is broken.

### Scenario A — same-session step handoff (no Redis required)

1. Start voice on step 1, fill enough to complete it. Tap Next.
2. Voice sheet auto-reconnects on step 2 (per the navigator wiring above).
3. **Expected:** agent's first utterance on step 2 references the participant's name from step 1: *"Hi Jane! Now I'd like to ask about your NDIS plan."*

If it doesn't:
- Check `bootstrap.prior_pages` is non-empty in the wire body for the step-2 session create.
- Check `participant_display_name` is populated.

### Scenario B — cross-day return (full Redis path)

1. Complete step 1 (any way — voice or manually).
2. Force-quit the app entirely. Wait 5 minutes (proves it's not in-memory cache).
3. Reopen, navigate to step 2, open voice sheet.
4. **Expected:** agent's first utterance references at least one fact from step 1.

If it doesn't, capture the server log for the session-create call:
- `session_create_tenant_id_missing` → Flutter is sending an empty `tenant_id`.
- `session_create_resolved_bootstrap` with `prior_pages_keys=[]` → bucket was empty for that `(tenant, participant)`. Most likely cause: `participant_id` differs between the two steps. Verify in the server access log that both calls used the same value.
- `session_create_resolved_bootstrap` with non-empty `prior_pages_keys` but agent still says "what's your name?" → backend prompt issue, not Flutter. Flag it.

### Scenario C — diagnostic endpoint (dev builds)

```
GET /v1/onboarding/_diag/bucket?tenant_id=t-xyz789&participant_id=p-abc123
```

Returns:

```json
{
  "bucket_empty": false,
  "summary_count": 2,
  "step_numbers": [1, 2]
}
```

Flutter dev builds can hit this **before** opening the voice sheet to confirm the bucket state matches expectations. (Endpoint is gated to `settings.environment != "production"`.)

### Scenario D — multi-tenant isolation

1. User belongs to two tenants A and B. Same human, two `participant_id`s (one per tenant).
2. Complete step 1 in tenant A's onboarding.
3. Switch to tenant B. Open voice sheet on tenant B's step 2.
4. **Expected:** the agent has NO memory of step 1 (different tenant_id → different bucket).

If the agent leaks data: that's a CRITICAL security bug. Capture the wire body of both session creates and compare `tenant_id`. They MUST differ.

## FAQ

**Q. Where do I get `tenant_id` from?**
The same place you get the active organisation in your existing app — typically `Get.find<OrgContext>().currentOrgId` or your equivalent. It's the org the participant is being onboarded into.

**Q. Is it OK to send `tenant_id` and `participant_id` even when the cross-screen feature is disabled?**
Yes. They're harmless when the feature flag is off. Server reads them and ignores them.

**Q. What if my participant deletes the app and re-installs?**
As long as auth restores the same `participant_id` (and they re-authenticate within 7 days), the bucket is still there. After 7 days, gone — they'll re-onboard from scratch.

**Q. Can I include `prior_pages` even when I think the server will hydrate from the bucket?**
Yes — Flutter-supplied `prior_pages` always wins over the bucket. This is the right call when you have fresher local data than what's in Redis (e.g. user just completed step 1 a second ago and the WS-close flush hasn't landed yet).

**Q. Does `tenant_id` come from auth headers or from the request body?**
**Right now: the request body** (`CreateSessionRequest.tenant_id`). The repo docstring says "auth context" — that's the long-term goal but not how it works today. Send it in the body. The auth-context migration is a separate backend ticket.

**Q. What if my user is in step 5 of a 6-step flow but they only ever did steps 1, 3, 5? (Skipped 2 and 4.)**
The bucket is keyed by step number, so the agent on step 5 will see prior_pages for steps 1, 3, and nothing for 2/4. That's correct — it'll mention what it knows and not pretend to know what it doesn't.

**Q. What if two devices are signed in as the same participant simultaneously?**
The Redis bucket is shared across devices (same `(tenant, participant)` key). Last write wins. The session-id index (`user_idx`) tracks every active session for diagnostics. WS-level locks prevent two voice sessions from writing to the same FormState concurrently, but they CAN take turns appending step summaries.

**Q. Do I need to clear the bucket when the participant logs out?**
No. The 7-day TTL handles natural decay. If you have a strong policy reason to clear (e.g. "delete my data" GDPR action), that's a separate backend endpoint outside this contract.

**Q. What does the agent see in its prompt?**
A `[LIVE_STATE_JSON]` block at the top of every system prompt. The `prior_pages` value from the bootstrap (whether Flutter-supplied or bucket-hydrated) is in there. The agent treats it as the only authoritative memory — anything not in the block does not exist as far as the agent is concerned.
