What this is #

SENA is an AI-powered, multi-tenant SaaS platform for Australian NDIS service providers. The onboarding service runs voice-driven participant onboarding using Google Gemini Live for real-time speech, with all form-state mutation, validation and tenant isolation handled by a Python FastAPI backend.

Architecture #

A 3-hop bridge: Flutter ↔ SENA backend ↔ Gemini Live. The backend is the broker — it relays audio, dispatches Gemini's tool calls, mutates Redis FormState, and emits typed WS events back to Flutter.

Why 3-hop and not direct (Flutter → Gemini)? Tool calls are how the screen updates. update_field, delete_repeatable_row etc. run on the SENA backend so the server is the source of truth for FormState, tenant isolation (NDIS APP), webhook delivery, and the cross-screen memory bucket. A direct connection would require porting ~1900 lines of tools.py + validators to Dart and giving Flutter authority over multi-tenant data. Not viable.

Session lifecycle #

From POST /v1/onboarding/session to the webhook landing in the app backend. One WS session = exactly one onboarding step.

① Flutter posts session

POST /v1/onboarding/session · body includes participant_id, tenant_id, step, schema, bootstrap. Server validates, creates FormState in Redis with TTL (session_max_sec), responds with session_id + ws_url.

② Bootstrap resolution

If bootstrap.prior_pages is empty AND cross-screen context enabled, server hydrates from the per-(tenant_id, participant_id) bucket. 2026-05-20 fix: the latest voice-captured name in the bucket beats Flutter's participant_display_name (so a name changed by voice in a prior session sticks).

③ Flutter opens WebSocket

WSS /ws/onboarding/{session_id} · server acquires per-session WS lock (Redis NX), constructs the Gemini Live bridge with system prompt (filtered schema), opens upstream connection to Gemini, emits ready event to Flutter.

④ Conversation loop

Flutter mic → backend → Gemini (16kHz PCM). Gemini transcribes, decides on tool calls. Server dispatches tools, mutates FormState, emits typed events (field_updated, row_added, state...). Gemini speech (24kHz PCM) flows back through the backend to Flutter.

⑤ Screen-state updates

Whenever Flutter UI changes (focus, dropdown toggle, row add/delete, validation flip) it emits screen_state_v2. The server's prompt builder uses field_status to filter the schema — hidden fields literally disappear from the model's view.

⑥ Silence watchdog

Background task polls every _SILENCE_POLL_SEC. After onboarding_silence_timeout_sec (default 8s) of no user audio AND Gemini not speaking, injects [SILENCE TIMEOUT] text into the Gemini session. Two-step protocol: gentle check-in, then summary recap. _silence_exhausted stops further fires after second strike.

⑦ advance_step

After all required fields are filled and the user confirms, Gemini calls advance_step(confirmation_transcript=...). Server runs validate_step_complete (cross-field invariants), serialises FormState, fires the webhook to the app backend with HMAC-SHA256 signature.

⑧ Webhook delivery

3-retry exponential backoff (1s → 4s → 16s). Emits step_completed event to Flutter with webhook_delivered flag. On all-retries-failed, Flutter has a REST polling fallback at GET /v1/onboarding/session/{id}/state.

⑨ Cleanup

WS closes, lock released, cross-screen bucket updated with this step's summary (5-concept verbatim: name, dob, gender, goals, hobbies_interests). Bucket TTL refreshed to 7 days.

Dialogue state machine #

Every conversational turn happens in exactly one of three states. The model identifies the state from pending_confirmation and next_forced_field in [LIVE_STATE_JSON].

ASKING(X) ──user_answers──> update_field(X, value, confidence) │ ┌─────────────────────────┴───────────────────────┐ │ │ confidence < 0.90 confidence ≥ 0.90 OR rejection.code == CONFIRM_REQUIRED │ │ │ ▼ ▼ AWAITING_CONFIRMATION(X) ──user "yes"──> ADVANCING ──> ASKING(next) │ └─user "no"──> ASKING(X) [re-ask]

States

① ASKING(slot)

Server has decided which slot is next. Model asks the question in ONE short sentence and stops. No tool call yet (no value to commit).

② AWAITING_CONFIRMATION

Captured a value with confidence < 0.90 → server returned CONFIRM_REQUIRED. pending_confirmation is locked. Only allowed move: re-commit on user "yes" with confidence: 1.0.

③ ADVANCING

Server committed from_slot. Model emits one-line ack ("Got it.") and immediately enters ASKING for next slot.

Hard invariants

FIELD-RENDER INVARIANT: a captured value DOES NOT EXIST until update_field returns {ok: true}. Forbidden:
  • "Got it, [value] is recorded" before {ok: true}
  • Treating CONFIRM_REQUIRED as a commit (it's the OPPOSITE)
  • Reading back from conversational memory instead of [LIVE_STATE_JSON]
Tool-BEFORE-talk mandate: NEVER verbally acknowledge a save/delete/update BEFORE the corresponding tool returned {ok: true}. Added 2026-05-20 after session 4339494d where the model said "consider that removed" WITHOUT calling delete_repeatable_row.

Validation layers #

Three concentric layers, all pure functions (no I/O). The dispatcher orchestrates; validators decide.

① Field rules

validators/field_rules.py — Per-(section, field) validators. Email format, AU phone regex, NDIS 9-digit, postcode 4-digit, DOB ≥ 18, enum membership, length caps, currency 9-digit cap.

② Cross-field

validators/cross_field.py — Invariants spanning multiple fields/rows. Plan end > start, emergency contact email/phone uniqueness + ≠ client's, medical history all-or-none, support schedule end>start, time slot non-overlap.

③ Sequencing

validators/sequencing.py — next_required_field, next_optional_field, section_min_unmet, validate_step_complete, validate_required_only. Honours visible_if AND screen_field_status.

Advisory vs strict mode

Controlled by SENA_AI_ONBOARDING_VOICE_VALIDATION_ADVISORY (default true). In advisory mode, validation failures emit field_advisory_warning but the value STILL commits — the participant can correct later. In strict mode, failures return {ok: false, rejection} and don't write.

System prompt structure #

The prompt is built per-turn by services/prompt_builder.py from prompts/onboarding_system.md. After the 2026-05-20 restructure, it has 10 numbered sections in dependency order.

§1
Absolute state authority. [LIVE_STATE_JSON] block + JSON-as-Truth Protocol (5 pre-flight rules) + behaviour-by-bootstrap-mode + context recovery for empty state.
§2
Screen is the source of truth. The [SCREEN] block from Flutter is the authoritative list. Schema = glossary, screen = checklist. No reciting hidden field names.
§3
Schema and tools. The schema JSON (pre-filtered by screen_field_status) + tools reference table.
§4
Dialogue state machine. States, the loop, conditional branching, field-render invariant, validation contract, tool honesty + tool-BEFORE-talk.
§5
Repeatable sections. Add/enter/exit procedure, FORBIDDEN list, parallel-field dictation, optional-field prompting.
§6
Address the participant. Greeting cadence (first-screen vs page_handoff — no "Hi" on subsequent screens) + name rules.
§7
Behavioural rules 1–24. Numbered rule list (see next section).
§8
Voice + interruption protocols. User interrupts mid-sentence; prolonged silence + [SILENCE TIMEOUT] handling; long sessions.
§9
Sequencing, pace, tone. One sentence default, one question per turn, Australian English warmth.
§10
Completion. advance_step protocol.
Why this matters: the prompt is what makes the agent reliable. Production sessions before the restructure showed the agent acting on training-data NDIS knowledge instead of the runtime schema (reciting plan_manager fields that Flutter had hidden). The current prompt explicitly subordinates training knowledge to [SCREEN].

Cross-screen memory bucket #

Per-(tenant_id, participant_id) Redis bucket. 7-day TTL refreshed on every write. Carries the 5-concept verbatim allowlist across step boundaries.

Why a bucket? The agent shouldn't ask "what's your name?" on every step. Step 1 captures the name; subsequent steps read it from the bucket. Step 3 sees prior_pages["step:1"]["name"] = "John" and addresses the participant by name without re-asking.

Silence watchdog #

Background task that re-engages a silent participant by injecting text into the Gemini session. gemini_live.py:752 _silence_monitor.

Two-step protocol

Fire 1 (8 s silence)

Injects [SILENCE TIMEOUT] text. Model reacts with "Hey, just checking — are you still there?". Sets _silence_warned = true.

Fire 2 (another 8 s)

Injects [SILENCE TIMEOUT — SUMMARY] with the pending-required field labels. Model says "When you're ready, we still need: X, Y, Z". Sets _silence_exhausted = true.

Reset

When new user audio arrives in _browser_to_gemini, _silence_warned and _silence_exhausted reset. Cycle restarts.

Suppression conditions

  • Gemini is currently speaking (_gemini_is_speaking == true) — don't talk over the agent.
  • _silence_exhausted == true — already fired twice; further pestering would be hostile.
  • onboarding_silence_timeout_sec <= 0 — entirely disabled.

Why text injection (not a tool call or WS event)

Gemini Live can't be triggered by anything except an incoming "turn". Injecting send_realtime_input(text="[SILENCE TIMEOUT]...") creates a synthetic user turn that includes its own self-describing prefix. The model recognises the prefix via §8 of the system prompt and reacts with the warm check-in template.
