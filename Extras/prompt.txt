## 1. Serving Approach — How does the platform call your AI services?

**What's decided:** The specs define individual API endpoints (`POST /v1/ocr/extract`, `POST /v1/voice/session`) and data flows (Mobile → LiveKit → GKE → Gemini → Postgres).

**What's missing — and this is the biggest gap in your entire architecture:**

Your specs describe your services calling **directly into Postgres**. But the platform team (Jill/Nishant) owns that database. Nobody has agreed on:

- **Who owns the database?** Does your AI layer write directly to their Postgres, or do you call *their* APIs to persist data?
- **Sync vs. Async contract?** When voice onboarding fills a form field, does your service write to the DB, or push an event that the platform consumes?
- **Service discovery:** How do the mobile/web apps route to your services? Through the platform's API gateway? A separate subdomain? Direct GKE ingress?

There are two clean options:

```
OPTION A: "AI as internal microservice"
┌─────────────┐     ┌──────────────────┐     ┌──────────────┐
│ Mobile/Web   │────▶│ Platform API GW   │────▶│ AI Services  │
│ (their team) │     │ (their team)      │     │ (your team)  │
└─────────────┘     └──────────────────┘     └──────────────┘
                           │                        │
                           ▼                        ▼
                    ┌──────────────┐         ┌──────────────┐
                    │ Platform DB   │◀────────│  AI DB       │
                    │ (theirs)      │ events  │  (yours)     │
                    └──────────────┘         └──────────────┘

OPTION B: "AI with shared DB access"
┌─────────────┐     ┌──────────────────┐     ┌──────────────┐
│ Mobile/Web   │────▶│ Platform API GW   │────▶│ AI Services  │
└─────────────┘     └──────────────────┘     └──────────────┘
                           │                        │
                           ▼                        ▼
                         ┌──────────────────────────┐
                         │     Shared Postgres       │
                         │  (AI gets read/write on   │
                         │   specific schemas only)  │
                         └──────────────────────────┘
```

Your current spec implicitly assumes **Option B** ("Agent writes directly to Postgres"). That's faster to build but creates tight coupling. This needs to be explicitly agreed with the platform team. **Ask Sandeep/Nishant: "Does your backend expose APIs we call, or do we get direct DB access?"**

**What's missing:**

These aren't things to spec in detail right now, but you need to **set up the GCP project and base infrastructure in Sprint 0** before any module work begins.

## 3. Multi-Tenancy Model — How is isolation enforced?

**What's decided:** This is your **most thoroughly covered** foundation. The docs specify:
- `tenant_id` on every table and vector index
- Row-Level Security (RLS) in Postgres
- Mandatory `WHERE tenant_id = :id` on every query
- `tenant_id` injected into AI system prompts
- Metadata-filtered vector search (single index, not per-tenant indexes)
- Designed for future migration to physical isolation

**What's missing:**

- **Who sets the `tenant_id` at the API boundary?** Your specs jump from "tenant_id exists" to "it's in the query." But *how does it get extracted from the incoming request and propagated through the call chain?* This ties directly into #4 (Auth).
- **Testing strategy:** How do you verify that a request from Tenant A can never retrieve Tenant B's data? This needs automated integration tests, not just code review. One missed `WHERE` clause = data breach = legal disaster in Australia.

## 4. Auth Strategy — How do requests prove identity?

**What's decided:** Almost nothing. This is the **second biggest gap**. The voice spec mentions a JWT token in the session response, but there's no spec for:

- **Who issues tokens?** Does the platform team's auth service issue JWTs that include `tenant_id`, and you validate them? Or do you have your own auth?
- **Token format:** What claims are in the JWT? At minimum you need `sub` (user), `tenant_id`, `role`.
- **Validation:** Does every AI service validate the JWT independently, or is there an API gateway that handles this?
- **Service-to-service auth:** When your AI service calls Vertex AI or writes to the DB, how is that authenticated?

The right answer for 95% of projects like this:

```
Platform team issues JWTs with tenant_id claim
    → Your API gateway (or middleware) validates the JWT
    → Extracts tenant_id
    → Passes it as context through every service call
    → Every DB query uses that tenant_id for RLS
```

**You must confirm:** Does the platform team already have an auth system (Firebase Auth, Auth0, custom)? Your AI layer should consume their tokens, not build its own auth.

## 5. OCR — Module Assessment

**What's decided:** Document AI for standard IDs, Gemini Flash fallback, GCS storage with 24h lifecycle, API contract defined.

**What's missing (minor):**
- Error handling for bad uploads (blurry images, wrong doc type, oversized files)
- Rate limiting per tenant
- Confidence threshold — what happens when confidence < 0.7? Does the frontend show a warning, or does the AI reject it?

**Verdict:** This is your **most implementation-ready** spec. The gaps are small and can be resolved during coding.

## 6. RAG — Module Assessment

**What's decided:** text-embedding-gecko, pgvector, Document AI for parsing, hybrid search (vector + keyword), cross-encoder reranking, citation with source/page/confidence.

**What's missing (significant):**
- **Chunking strategy validation:** The spec says 1000 char chunks with 100 overlap. This is a starting point but needs empirical testing. NDIS policy documents may have tables/lists that break with naive character splitting.
- **No evaluation framework:** How will you measure if RAG answers are accurate? "Almost 100% accuracy" was the client's stated expectation. You need a test set of question-answer pairs against real NDIS documents.
- **Document update lifecycle:** When a policy PDF is updated, what happens to the old vectors? Full re-index or incremental?
- **NDIS "SYSTEM" documents:** The spec mentions `tenant_id = 'SYSTEM'` for shared NDIS policies. Who uploads these? How are they distinguished from tenant-specific docs?

**Verdict:** Solid design, but **blocked on sample policy PDFs** from Sandeep. The evaluation question ("how do we know the answers are right?") is the hardest unsolved problem here.
